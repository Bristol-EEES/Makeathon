# Troubleshooting

Switch off motor power before changing wiring. Work through one subsystem at a time, and ask a supervisor if a component becomes hot, smells unusual, or appears damaged.

| Symptom | Possible Cause | What to Check |
|---|---|---|
| Pico powers up but no `RPI-RP2` drive appears | BOOTSEL was not held while USB was connected, the cable is charge-only, or the USB port is unsuitable | Disconnect USB. Hold BOOTSEL while reconnecting with a known data-capable cable, then release it after connection. Try another USB port if necessary. |
| Pico does not appear in Thonny | Wrong interpreter or port, charge-only USB cable, or missing firmware | Check the cable, select the Pico's MicroPython interpreter and USB/serial port, then reconnect. |
| `RPI-RP2` appears but Thonny cannot connect | The Pico is still in bootloader mode or MicroPython firmware is missing | Copy the current stable original-Pico MicroPython `.uf2` onto `RPI-RP2`, allow the board to reboot automatically, then select its Pico/RP2040 MicroPython interpreter and serial/COM port in Thonny. |
| Code runs on the computer instead of the Pico | Desktop Python interpreter is selected | Select the MicroPython interpreter for the Raspberry Pi Pico/RP2040—not Local Python or Thonny's Python—and select the Pico's USB/serial or COM port. |
| A program uses the wrong Pico pin | A physical header-pin number was used as a GPIO number | `Pin(15)` means GP15, not physical header pin 15. Use the Pico pinout and the GPIO and physical-pin columns in the [authoritative wiring table](../wiring/full_system_wiring.md). |
| Thonny says the device is busy | A program is still running, or another application has locked the serial connection | Press Stop/Interrupt; close other serial tools; restart Thonny's interpreter and reconnect if necessary. |
| Changes do not appear after restart | The edited file was saved only on the computer, or a different Pico file is running | Inspect the files stored on the Pico and check where Thonny saved the `.py` file. |
| Robot works while connected to Thonny but does nothing after USB is unplugged | The program was only run from Thonny, was saved to the computer instead of the Pico, is not named `main.py`, contains a startup error, or the Pico lacks standalone power | Reconnect to Thonny and inspect the Pico's files. Confirm `main.py` exists if automatic startup is intended, run it manually and fix any errors, then—with power removed—confirm the documented standalone power and common-ground connections. Disconnect USB and retest. |
| Code will not run | Syntax/runtime error, wrong interpreter, board busy, or problematic `main.py` | Read the first shell error; select MicroPython and the Pico; press Stop/Interrupt; restart and test a minimal non-robot program. |
| Left IR sensor always reads the same value | Incorrect VCC/GND wiring, GP14 disconnected, unsuitable threshold, or wrong height | Confirm `3V3(OUT)`, common GND, and Left IR OUT → GP14, then follow the [IR sensor calibration guide](../guides/ir_sensor_calibration.md). |
| Right IR sensor always reads the same value | Incorrect VCC/GND wiring, GP15 disconnected, unsuitable threshold, or wrong height | Confirm `3V3(OUT)`, common GND, and Right IR OUT → GP15, then calibrate it over both surfaces. |
| Sensor reacts backwards | Module output sense differs from the assumption, or light/dark surfaces are reversed | Use the [calibration procedure](../guides/ir_sensor_calibration.md) to record the actual HIGH/LOW state over line and background; adapt your interpretation rather than rewiring power. |
| Sensor reading is unstable | Sensor is near its threshold, mounting height is changing, ambient light is varying, or wiring is loose | Secure the mounting and wiring, then recalibrate under lighting similar to the event conditions. |
| The two sensors behave differently | Their mounting, threshold settings, or component tolerances differ | Calibrate each sensor separately at its intended height using the [IR sensor calibration guide](../guides/ir_sensor_calibration.md). |
| Left and right IR readings appear swapped | Modules are mounted on opposite sides, OUT wires reach the opposite GPIO, or left/right was judged from an observer's viewpoint | Left and right are from the robot's perspective while facing forward. Place a card or line beneath one sensor at a time while printing GP14 and GP15, then power off and correct only the crossed OUT connections or labels. Do not change the canonical GPIO table. |
| Ultrasonic #1 always reads zero / no Echo | Missing 5 V VCC, missing common GND, GP10/GP11 reversed, divider error, unsuitable orientation/target, or incorrect code timing | Check GP10 → TRIG and divided ECHO → GP11, inspect both divider resistors, then test against a large solid object. |
| Ultrasonic #2 always reads zero / no Echo | Missing 5 V VCC, missing common GND, GP12/GP13 reversed, divider error, unsuitable orientation/target, or incorrect code timing | Check GP12 → TRIG and divided ECHO → GP13, inspect both divider resistors, then test against a large solid object. |
| Ultrasonic reading is constant or impossible | Trig and Echo reversed, incorrect timing, poor target surface, electrical noise, or invalid GPIO mapping | Verify the pin mapping and divider, then use one sensor with a large flat target and the isolated test code. |
| Ultrasonic distance is incorrect or noisy | Loose divider connection, wrong resistor value, floating ground, long jumper wires, motor noise, poor target surface, reflections, or readings taken too quickly | Remove power; verify 1 kΩ and 2 kΩ placement and common GND. Shorten/secure wires, stop motors for an isolated test, face a large flat target, and add time between readings. |
| Two ultrasonic sensors interfere with each other | Both modules transmit at the same time and one receives the other's echo | Trigger and finish reading one module before triggering the other; leave a short pause between measurements. |
| Pico becomes unstable after an ultrasonic sensor is connected | Echo may be connected directly at approximately 5 V, the divider may be wired incorrectly, or common ground may be missing | Disconnect power immediately. Confirm ECHO enters the 1 kΩ resistor, the Pico input uses the midpoint, the 2 kΩ resistor reaches GND, and all grounds are common. |
| Left motor does not move | Missing motor supply, disabled channel, loose OUT1/OUT2 wire, stalled mechanism, or wrong control state | Check GP2 → IN1, GP3 → IN2, GP4 → ENA, and the left motor on OUT1/OUT2. Test with wheels clear. |
| Right motor does not move | Missing motor supply, disabled channel, loose OUT3/OUT4 wire, stalled mechanism, or wrong control state | Check GP6 → IN3, GP7 → IN4, GP8 → ENB, and the right motor on OUT3/OUT4. Test with wheels clear. |
| One motor does not move after ENA/ENB wiring | Wrong enable GPIO, zero PWM duty, jumper/configuration error, invalid direction state, missing common ground, or a motor/output fault | Test one channel with wheels raised: GP4 → ENA or GP8 → ENB, 100% PWM, and a known Direction A/B input state. Confirm the relevant enable jumper is removed if it ties EN HIGH. If it still fails, check common GND and the motor/output wiring before reducing PWM. |
| Motor runs only at full enable or ignores PWM | The ENA/ENB jumper may still be holding that enable input HIGH, or PWM may be connected to the wrong enable pin | Switch power off. Check that GP4 reaches ENA and GP8 reaches ENB, and remove only the corresponding enable jumper if it permanently ties the input HIGH. Do not confuse these with the separate 5V-EN/regulator jumper. |
| Motor moves in the wrong direction | Motor leads are reversed relative to the intended physical direction | Identify that motor, power off, then swap its two output wires or account for its mounting in your own control logic. Never reverse the battery. |
| Robot spins in place instead of driving forward | One motor has opposite output-wire polarity, uses the opposite Direction A/B state, or the left/right motor outputs are confused | Raise the wheels and run each motor separately using the intended forward command. Confirm both wheels would propel the robot forward. With all power disconnected, swap only the two output wires of the reversed motor, or invert that motor's direction logic. |
| Motor hums, twitches, or starts only after being pushed | PWM is too low to overcome static friction, the mechanism is jammed, the battery is weak, a connection is loose, the enable channel is misconfigured, or the available startup current is insufficient | Raise the wheels and check for rubbing or a jam. Test the channel briefly at 100% enable with a known direction state, then reduce PWM gradually to find a reliable running range. There is no universal minimum duty cycle; L298N voltage drop and mechanical load also matter. |
| Motors behave inconsistently | Weak batteries, loose connections, mechanical rubbing, electrical noise, or overly high load | Check battery condition, terminals, common ground, wheel freedom, and whether behaviour changes when each motor is tested alone. |
| Pico resets or disconnects when motors start | Battery sag, poor grounding, electrical noise, or motor current entering the control-power path | Stop; check the power architecture and common ground, tighten connections, and ask a supervisor to review the supply arrangement. Do not bypass protection or guess at new power links. |
| Robot turns the wrong way | Left/right motors or sensors are confused, or one motor's physical forward direction differs | Label each sensor and motor; test each independently; write down actual directions before combining the system. |
| Several devices behave unpredictably | Pico and L298N do not share common GND, or a sensor ground is missing | With all power disconnected, trace battery negative, L298N GND, Pico GND, both IR grounds, and both HC-SR04 grounds to the common GND rail. Missing common ground can cause ignored motor commands, unstable sensor values, ultrasonic failures, and inconsistent HIGH/LOW readings. |
| Breadboard circuit appears unpowered or behaves inconsistently | Split power rail, wire placed one row away, loose jumper, component lead not making contact, or an accidental connection between the 5 V and 3.3 V rails | Disconnect battery and USB power. Check rail continuity and every row position physically; reseat loose leads; confirm the 5 V and 3.3 V rails remain separate and that no connected row creates a short. |
